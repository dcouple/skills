# SEO content drafting

Produce the requested draft or project content changes. Drafting does not imply permission to publish.

## Inputs

- Read the approved strategy or direct brief, target audience/query, voice guidance, and relevant existing pages.
- Missing a formal strategy file is not a blocker when the request supplies enough direction. Clarify only choices that materially affect scope or claims.
- Use `page-strategy` when the premise needs work and `seo-writing-framework` for the writing process.

## Research and write

1. Inspect current search results and primary sources for the topic; note dates, evidence gaps, and existing coverage.
2. Answer the reader's job before promoting a product. Apply fair criteria and real limitations to comparisons.
3. Draft using the project's actual format: for example Markdown, a CMS entry, a template, or an application route.
4. Preserve supported claims and citations. Do not invent experience, credentials, statistics, or testimonials.
5. Review for clarity, useful examples, and voice; use `page-review` when available for intent and promotion checks.

## Integrate when requested

- Follow existing content registration, metadata, author/date, social-image, and component conventions.
- Use accurate schema only where applicable; verify current eligibility and implementation guidance.
- Add relevant internal links and discoverability through the site's actual navigation or index. Not every page belongs in the footer.
- Inspect sitemap, route, deployment, and cache conventions; update per-page entries only where this project needs them.
- Keep dates truthful. Do not backdate new work to imply earlier publication or refresh dates without real updates.

## Verify

- Run project-specific checks, such as content linting, link validation, build, and rendered-page inspection.
- Check the actual output: text, links, layout, metadata, and public route where available.
- Report completed pages, sources, checks, missing proof, and remaining publication steps.
- Commit, push, or prepare a PR only when authorized. Do not treat a PR as deployed.

## After authorized publication

- Verify the live URLs before discussing indexing status.
- Use only an authorized indexing channel whose current documentation confirms support for this site/content type. A connected account or key alone is not permission or eligibility.
- Distinguish a request accepted by a service from a page actually indexed. If submission is unsupported, provide the relevant manual next step.
- Record meaningful changes, baselines, and review dates with `seo-data-organize`; use one experiment history, not duplicate files.

## Shared artifacts

If Grain is connected, save research, drafts, reviews, URL lists, and experiment records in the shared task folder; pass its ID/storage rule downstream. Project source files remain in their required locations, with local artifact copies allowed. Otherwise use normal storage silently. Do not automatically commit analytics or expose sensitive data.
